1. Complete Structure of a Compiler (Analysis–Synthesis Model)

A Compiler translates a high-level source program into an equivalent low-level target machine program while reporting syntax and semantic errors. It consists of six sequential phases supported by two cross-cutting modules—the Symbol Table Manager and Error Handler—divided into a language-dependent Front-End (Analysis) and a machine-dependent Back-End (Synthesis).

2. Step-by-Step Phase Trace on position = initial + rate * 60

  1. Lexical Analysis (Scanner): Groups characters into tokens: <id,1> <=> <id,2> <+> <id,3> <*> <60>.
  2. Syntax Analysis (Parser): Builds a hierarchical Parse Tree / AST verifying grammatical rules (operator precedence: * before +).
  3. Semantic Analysis: Checks type compatibility and inserts coercion: inttofloat(60) if rate is float.
  4. Intermediate Code Generation: Produces machine-independent Three-Address Code (TAC): t1 = inttofloat(60); t2 = id3 * t1; t3 = id2 + t2; id1 = t3.
  5. Code Optimization: Eliminates redundant instructions: t1 = id3 * 60.0; id1 = id2 + t1.
  6. Target Code Generation: Allocates registers and emits assembly: LDF R2, id3; MULF R2, R2, #60.0; LDF R1, id2; ADDF R1, R1, R2; STF id1, R1.

3. Passes, Front-End vs. Back-End & Lexical Error Impact

  • Compiler Pass: One complete traversal over the source or intermediate representation (e.g., Front-End Pass 1 + Back-End Pass 2).
  • Front-End vs. Back-End (Java Example): Front-End (javac) performs lexical, syntax, and semantic analysis to generate platform-independent Java Bytecode (.class); Back-End (JVM JIT) optimizes bytecode and generates native x86/ARM machine instructions.
  • Impact of Lexical Errors (IMP Q4): If the lexer misclassifies tokens or drops characters, the parser receives malformed token streams causing cascading syntax errors, semantic type-lookup failures, and invalid intermediate code.

1. Token, Lexeme, Pattern & Token Stream Example (IMP 5M Q3)

  • Token: A pair <token-name, attribute-value> representing a lexical category (e.g., keyword, id, operator).
  • Lexeme: The actual sequence of source characters matching a pattern (e.g., total, 10).
  • Pattern: A regular expression rule describing the valid strings for a token (e.g., [a-zA-Z_][a-zA-Z0-9_]*).
  • Trace for int total = a + 10: int (Keyword), total (Identifier), = (Assignment Op), a (Identifier), + (Arithmetic Op), 10 (Integer Constant).

2. Lexical Analyzer Interaction & Input Buffering (Two-Buffer Scheme with Sentinels)

The Parser calls getNextToken(); the Lexer reads characters using a Two-Buffer Scheme (each buffer of size $N = 4096$ bytes terminated by an eof sentinel) with two pointers: lexemeBegin and forward. Using sentinels reduces end-of-buffer checks from two tests per character to one, avoiding the lookahead truncation problem of a single buffer (IMP 5M Q5).

1. Regular Expressions for Common Tokens (General 5M Q13 & IMP 10M Q1, Q9)

  • Identifiers: [a-zA-Z_][a-zA-Z0-9_]*  |  Special variable #name123 (IMP Q1): #[a-zA-Z]+[0-9]+
  • Integers: [+-]?[0-9]+  |  Floating-Point Numbers: [+-]?[0-9]+(\.[0-9]+)?([eE][+-]?[0-9]+)?
  • Calculator Operators (IMP Q9): [+\-*/]

2. Complete Pipeline Example: (a+b)*abb → NFA (Thompson) → DFA (Subset Construction) → Minimized DFA

  1. Step 1 – Thompson's Construction (RE → $\epsilon$-NFA): Builds $\epsilon$-transitions for union (a|b), Kleene closure * loop from end back to start, and sequential concatenation a → b → b across states $0$ through $10$ (accepting state $\{10\}$).
  2. Step 2 – Subset Construction ($\epsilon$-NFA → DFA): Compute $\epsilon\text{-closure}$ states:
    • $A = \epsilon\text{-closure}(0) = \{0, 1, 2, 4, 7\}$ (Start State). On $a \rightarrow B = \{1, 2, 3, 4, 6, 7, 8\}$; on $b \rightarrow A$.
    • From $B$: on $a \rightarrow B$; on $b \rightarrow C = \{1, 2, 4, 5, 6, 7, 9\}$.
    • From $C$: on $a \rightarrow B$; on $b \rightarrow D = \{1, 2, 4, 5, 6, 7, 10\}$ (Accepting State).
    • From $D$: on $a \rightarrow B$; on $b \rightarrow A$.
  3. Step 3 – DFA Minimization (Hopcroft's Partition Refinement): Partition into Accepting $\{D\}$ and Non-Accepting $\{A, B, C\}$. Splitting on input $b$ separates $C$ (goes to $D$) from $\{A, B\}$; splitting on $a$ separates $A$ (goes to $B$) from $B$ (loops to $B$). All 4 states $\{A, B, C, D\}$ are distinct—yielding the minimal 4-state DFA!

3. Why DFA is Preferred Over NFA & Minimization Benefits (IMP 5M Q4 & Q9)

An NFA allows multiple transitions per symbol and $\epsilon$-moves, requiring $O(|S|^2 \cdot n)$ backtracking simulation, whereas a DFA has at most one deterministic transition per symbol, recognizing tokens in strict $O(n)$ linear time (one lookup per character). DFA Minimization merges indistinguishable states, shrinking transition tables in compiler memory and L1 CPU cache.

1. Lex & Yacc Architecture and Workflow

  • Lex (Lexical Analyzer Generator): Takes a .l specification file containing Regular Expressions + C actions, compiles it into lex.yy.c containing a minimized DFA transition table and yylex() function.
  • Yacc (Yet Another Compiler-Compiler): Takes a .y Context-Free Grammar file and generates an LALR(1) parser in y.tab.c with yyparse(), which repeatedly invokes yylex() to build ASTs or generate code.
  • Without Lex & Yacc (IMP 10M Q10): Developers must manually write regex-to-DFA converters, buffer management, FIRST/FOLLOW calculators, and LALR state tables—increasing development time and bug rates dramatically.

2. Lexical Error Recovery Techniques & Panic Mode on "@" (IMP 5M Q7)

  • Panic Mode Recovery: When the lexer encounters an illegal character like "@" that matches no pattern, it deletes successive characters from the remaining input until it reaches a well-formed token delimiter (such as whitespace, ;, or )), reports one clean error, and resumes scanning—preventing infinite error cascades (IMP 10M Q3).
  • Other Techniques: Deleting an extraneous character, inserting a missing character, replacing an incorrect character, or transposing two adjacent characters.

1. Context-Free Grammar (CFG)

A CFG is a 4-tuple $G = (V, T, P, S)$ where $V$ is a finite set of non-terminals, $T$ is a finite set of terminals ($V \cap T = \emptyset$), $P$ is a finite set of production rules $A \rightarrow \alpha$ ($A \in V, \alpha \in (V \cup T)^*$), and $S \in V$ is the start symbol.

Example Expression Grammar: $E \rightarrow E + E \mid E * E \mid (E) \mid \text{id}$.

2. Leftmost vs. Rightmost Derivation & Parse Trees

  • Leftmost Derivation (LMD): Replaces the leftmost non-terminal at every step. For id + id * id: $E \Rightarrow E + E \Rightarrow \text{id} + E \Rightarrow \text{id} + E * E \Rightarrow \text{id} + \text{id} * E \Rightarrow \text{id} + \text{id} * \text{id}$.
  • Rightmost Derivation (RMD / Canonical Derivation): Replaces the rightmost non-terminal at every step.
  • Parse Tree: Graphical tree representation of a derivation where root is $S$, interior nodes are non-terminals, and leaves read left-to-right yield the derived string.

3. Ambiguity in Grammars & Twisted Questions (Twisted 5M Q4–Q6)

  • Definition: A CFG is ambiguous if there exists at least one string $w \in L(G)$ that has two or more distinct Parse Trees (equivalently, two distinct leftmost derivations). For id + id * id under $E \rightarrow E+E \mid E*E \mid \text{id}$, one tree groups (id + id) * id and another groups id + (id * id).
  • Why Undesirable (Twisted 5M Q6): Ambiguity gives a single program multiple conflicting meanings (violating operator precedence/associativity), making deterministic compilation impossible.
  • Can two different parse trees produce the same LMD? (Twisted 5M Q5): No—there is a strict one-to-one bijection between Parse Trees and Leftmost Derivations.
  • Ambiguity vs. Nondeterminism (Twisted 5M Q4): Ambiguity means multiple parse trees exist for one string (inherent semantic conflict); Nondeterminism means a top-down parser cannot choose a unique production with 1-token lookahead (e.g., common prefixes $A \rightarrow \alpha\beta_1 \mid \alpha\beta_2$), even when the grammar is completely unambiguous!

1. Left Recursion & Elimination Algorithm

A grammar is left-recursive if a non-terminal $A$ derives a string starting with itself ($A \Rightarrow^+ A\alpha$). Left recursion causes top-down Recursive Descent parsers to loop infinitely (Twisted 5M Q7).

  • Immediate Left Recursion Rule: Replace $A \rightarrow A\alpha_1 \mid A\alpha_2 \mid \beta_1 \mid \beta_2$ with: $$A \rightarrow \beta_1 A' \mid \beta_2 A'$$ $$A' \rightarrow \alpha_1 A' \mid \alpha_2 A' \mid \epsilon$$
  • Example: $E \rightarrow E + T \mid T$ becomes $E \rightarrow T E'$, $E' \rightarrow + T E' \mid \epsilon$.

2. Left Factoring

Left Factoring rewrites productions sharing a common prefix $A \rightarrow \alpha\beta_1 \mid \alpha\beta_2$ into $A \rightarrow \alpha A'$ and $A' \rightarrow \beta_1 \mid \beta_2$, deferring the decision until enough tokens are seen.

3. Twisted Conceptual Questions (Twisted 10M Q2 & 5M Q1–Q3)

  • Which Transformation First? (Twisted 10M Q2): Eliminate Left Recursion FIRST, then apply Left Factoring, because left-recursion removal introduces new right-recursive productions that may expose new common prefixes.
  • Can a left-factored, non-left-recursive grammar still fail LL(1)? (Twisted 5M Q1 & Q3): Yes! If the grammar is ambiguous (e.g., dangling-else) or has FIRST/FOLLOW conflicts on nullable productions, it remains non-LL(1).
  • Is every ambiguous grammar left-recursive? (Twisted 5M Q2): No (e.g., $S \rightarrow aSbS \mid bSaS \mid \epsilon$ is ambiguous without left recursion).

1. Recursive Descent & Predictive LL(1) Parsing

Recursive Descent Parsing uses a set of mutually recursive procedures (one per non-terminal). When the grammar is LL(1) (Left-to-right scan, Leftmost derivation, 1-token lookahead), a Predictive Parser uses an explicit stack and a 2D parsing table $M[A, a]$ to parse deterministically with zero backtracking (agreeing with Twisted 10M Q3).

2. Conditions for a Grammar to be LL(1)

For every pair of distinct productions $A \rightarrow \alpha \mid \beta$: (1) $\text{FIRST}(\alpha) \cap \text{FIRST}(\beta) = \emptyset$; (2) at most one of $\alpha, \beta$ can derive $\epsilon$; and (3) if $\beta \Rightarrow^* \epsilon$, then $\text{FIRST}(\alpha) \cap \text{FOLLOW}(A) = \emptyset$.

1. Shift-Reduce Parsing, Handles & Four Actions

Shift-Reduce Parsing constructs a parse tree bottom-up by shifting input symbols onto a stack until the top of the stack matches the right-hand side of a production (called a Handle), then replacing (pruning) that handle with the left-hand non-terminal (Handle Pruning).

  • Four Actions: (1) Shift next input token onto stack; (2) Reduce handle $\beta$ on top of stack to $A$; (3) Accept when stack holds $S and input is $; (4) Error when no valid move exists.
  • Shift-Reduce Conflict Resolution (Twisted 10M Q8): Occurs when the parser cannot decide whether to shift another token or reduce (e.g., dangling-else). Resolved by specifying operator precedence/associativity rules (in Yacc: %left, %right) or resolving the dangling-else by preferring Shift (binding else to nearest if).

2. Operator Precedence Parsing & Twisted Cases (Twisted 10M Q14 & 5M Q12)

An Operator Grammar has no $\epsilon$-productions and no two adjacent non-terminals. It uses three precedence relations between terminals $a$ and $b$: $a \lessdot b$ ($a$ yields precedence to $b$), $a \doteq b$ (equal precedence, e.g., ( and )), and $a \gtrdot b$ ($a$ takes precedence over $b$—triggers handle reduction).

  • Undefined Relational Operator Entry (Twisted 10M Q14): If the parser encounters an empty cell between two relational operators (e.g., a < b < c), it invokes a syntax error handler reporting non-associativity of relational operators.
  • Why Not Suitable for All CFGs (Twisted 5M Q12): Cannot handle grammars with $\epsilon$-productions, adjacent non-terminals, or tokens having dual unary/binary roles (like unary minus vs. binary minus).

  • 1. Panic Mode Recovery (Fastest & Most Widely Used — Twisted 5M Q17): Discards input tokens one at a time until a designated synchronizing token (such as ;, }, or end) is found, pops stack states until parsing can resume cleanly, and guarantees termination without infinite loops.
  • 2. Phrase-Level Recovery: Performs local correction on the remaining input (e.g., inserting a missing semicolon or replacing a comma with a semicolon) and continues parsing; requires careful design to avoid infinite insertion loops.
  • 3. Error Productions: Augments the grammar with explicit rules capturing common programmer mistakes (e.g., stmt → expr missing ;) to emit user-friendly diagnostic messages.
  • 4. Global Correction: Finds the minimal edit-distance parse tree for an erroneous string (theoretically optimal but too slow $O(n^3)$ for practical compilers).
  • Can a parser recover from every syntax error? (Twisted 5M Q18): No—severely corrupted code with cascading unclosed braces or structural mangling may force the parser to skip large blocks or abort once sync tokens are exhausted.

1. Semantic Analysis, Type Systems & Type Checking (Twisted 10M Q6, Q13, Q14)

Semantic Analysis verifies context-sensitive meaning beyond syntax (undeclared variables, type mismatches, array bounds, argument counts). A Type System assigns type expressions (e.g., int, float, array(10, int), pointer(T)) to constructs.

  • Type Conversions (Widening vs. Narrowing / Coercion): Automatic implicit conversion is called Coercion (e.g., widening int to float in 3 + 4.5 without data loss).   • Structural Equivalence: Two types are equivalent if they have identical internal structure and field types (even with different names).

A Symbol Table stores identifier names, types, scopes, memory offsets, and function signatures. Lookup occurs far more frequently than insertion (every variable reference vs. one declaration, Twisted 5M Q7). Linear lists take $O(n)$ per lookup (slow for large programs, Twisted 5M Q17); production compilers use Chained Hash Tables linked via parent-scope pointers (LeBlanc-Cook symbol table stack) achieving $O(1)$ average lookup across nested lexical blocks.

1. Three-Address Code (TAC), AST & DAG

Three-Address Code (TAC) is a linearized intermediate representation where every instruction has at most three operands (two sources + one result, e.g., x = y op z). Common TAC types: binary assignments (x = y + z), unary assignments (x = -y), copy statements (x = y), unconditional/conditional jumps (goto L, if x relop y goto L), and indexed/pointer operations.

  • AST vs. Parse Tree & DAG (Twisted 5M Q1): An AST strips redundant punctuation/parentheses from a Parse Tree. A Directed Acyclic Graph (DAG) merges identical subtrees (common subexpressions) into shared nodes. An AST is structurally identical to a DAG only when the expression contains zero repeated subexpressions.
  • Worked Example 1 — a := b * -c + b * -c (General 10M Q1): In the DAG, uminus(c) and *(b, uminus(c)) are created only once and shared by both inputs of +, reducing TAC to: t1 = -c; t2 = b * t1; t3 = t2 + t2; a = t3.

2. Tabular Representations for x = (a + b) * (c + d) - (a + b) (General 10M Q2 & IMP 10M Q1)

TAC: (0) t1 = a + b → (1) t2 = c + d → (2) t3 = t1 * t2 → (3) t4 = t3 - t1 → (4) x = t4.

1. Backpatching in Single-Pass Compilers (General 5M Q6, IMP 5M Q2 & Twisted 5M Q4)

Backpatching enables single-pass intermediate code generation for forward jumps whose target label addresses are not yet known when the jump instruction is emitted. The compiler maintains three lists of unresolved jump indices—truelist, falselist, and nextlist—and uses makelist(i), merge(p1, p2), and backpatch(p, L) to fill in target addresses once label L is reached.

2. Short-Circuit Boolean Translation: a < b OR c < d AND e < f (General 10M Q3 & IMP 10M Q3)

Because AND has higher precedence than OR, if a < b is true, evaluation jumps immediately to L_true without evaluating the rest:

100: if a < b goto L_true
101: goto 102
102: if c < d goto 104
103: goto L_false
104: if e < f goto L_true
105: goto L_false

Strict vs. Short-Circuit (Twisted 5M Q3): Strict evaluation computes boolean temporaries t1 = A; t2 = B; t3 = t1 or t2 before branching, evaluating both operands even when A is already true.

1. Switch-Case Translation Strategies (Dense vs. Sparse Cases — Twisted 10M Q3)

  • 1. Sequential Conditional Tests (< 5 cases): Emits linear chain if x == v1 goto L1; if x == v2 goto L2; ... goto L_default.

1. Leader Algorithm & Basic Block Partitioning (General 10M Q3 & IMP 10M Q1)

A Basic Block is a maximal sequence of consecutive TAC instructions with a single entry point (first instruction) and single exit point (last instruction). Leader Rules: (1) First statement is a leader; (2) Any target of a conditional/unconditional jump is a leader; (3) Any statement immediately following a jump is a leader.

  • Trace on Matrix Initialization (General 10M Q3): Leaders are Statement (1) i = 1, Statement (2) j = 1 (target of line 10), and Statement (3) t1 = 10 * i (target of line 8). Forms B1: (1) → B2: (2) → B3 (Inner Loop): (3)–(8) with self-loop back-edge to B3 → B4 (Outer Loop): (9)–(10) with back-edge to B2 → EXIT.
  • Trace on Product Loop (IMP 10M Q1): Leaders are (1) prod = 0 and (3) t1 = 4 * i. Forms Entry → B1 (1–2) → B2 (3–7) (with back-edge B2 → B2) → Exit.

2. Basic Block Optimization via DAG (General 10M Q4 & IMP 10M Q2)

Given: (1) a = b + c; (2) d = b + c; (3) e = a + d; (4) b = e * c; (5) d = b + c;

In the DAG, statements (1) and (2) share a single +(b0, c0) node labeled {a, d}. Statement (3) creates e = +(a, a). Statement (4) updates b to *(e, c0), and statement (5) computes d = +(b_new, c0). Optimized TAC (4 instructions instead of 5):
a = b + c; e = a + a; b = e * c; d = b + c; (eliminating redundant computation of d).

3. Loop Optimization, Peephole Optimization & Modern Compilers (LLVM/GCC)

  • Loop Optimizations: Code Motion moves loop-invariant computations outside the loop; Induction Variable Elimination removes redundant loop counters; Reduction in Strength replaces expensive operations like 4 * i with cheap additions t = t + 4.
  • Peephole Optimization: Scans a small sliding window of target instructions to apply local improvements: (1) redundant load/store elimination, (2) unreachable code removal, (3) algebraic identities (x + 0 = x, x * 1 = x), and (4) strength reduction (x * 2 → x << 1).
  • LLVM & GCC Modularity (General 5M Q8): Both use a three-phase retargetable architecture (Language Front-End → Common IR Optimizer [LLVM IR / GIMPLE] → Target Back-End), allowing $M$ languages and $N$ CPUs with $M + N$ components instead of $M imes N$.

1. Major Issues in Code Generator Design (General 10M Q2 & IMP 10M Q5)

  • Input to Code Generator: Linear IR (TAC/Quadruples) assumed type-checked and bug-free.
  • Target Machine Architecture: RISC vs. CISC instruction sets, addressing modes, register count, and instruction costs.
  • Runtime Storage Management: Mapping variable names to static, stack, or heap addresses.
  • Instruction Selection: Choosing fast, low-cost machine idioms (e.g., INC R0 instead of ADD R0, #1).
  • Register Allocation vs. Assignment (General 5M Q7 & IMP 5M Q3): Register Allocation selects which variables reside in fast CPU registers; Register Assignment picks the specific register (e.g., R1) for each allocated variable (NP-complete via graph coloring).

2. Next-Use Information & Simple Code Generator Trace for x = y + z (General 10M Q5 & IMP 10M Q4)

Next-Use Information (computed via a backward scan over each basic block) tells the code generator whether a variable's current value will be read again before being overwritten; dead registers can be reused immediately without spilling to RAM.

Using Register Descriptors (what variable each register currently holds) and Address Descriptors (locations where a variable's current value resides), getReg(x = y + z) selects register R for x (reusing y's register if y has no next-use), emits MOV R, y (if y is not already in R), emits ADD R, z, and updates descriptors so x is exclusively in R.

  • Google Maps vs. Static Map & Dynamic Markers (10M Q1, Q4 & 5M Q1): Interactive Maps SDK supports zooming, panning, gesture controls, and dynamic GoogleMap.addMarker(MarkerOptions()) clustering, whereas static maps return a single non-interactive bitmap image. Runtime location permissions (ACCESS_FINE_LOCATION) must be requested via ActivityResultContracts.RequestPermission with SecurityException checks to prevent crashes.
  • Geocoding vs. Reverse Geocoding (10M Q2, Q5 & 5M Q2): Geocoding converts a street address into (latitude, longitude); Reverse Geocoding converts coordinates into a human-readable address via Android's Geocoder class. Always check Geocoder.isPresent(), run off the main UI thread, and handle IOException or empty result lists gracefully.
  • App Signing, Versioning & Play Store Publishing (10M Q3, Q6 & 5M Q3–Q5): Every APK/AAB must be cryptographically signed with a developer keystore (verifying author authenticity and update integrity). versionCode is an internal strictly increasing integer used by Play Store for upgrades, while versionName is the user-visible string (e.g., "2.1.0"). Multi-region builds use Gradle productFlavors with distinct applicationIdSuffix and signing configs before uploading a signed Android App Bundle (.aab) to Google Play Console.
