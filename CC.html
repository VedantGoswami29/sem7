1. Definition of Cloud Computing

Cloud Computing is the on-demand delivery of IT resources—such as compute power, database storage, applications, networking, and intelligence—over the Internet with pay-as-you-go pricing. According to the NIST (National Institute of Standards and Technology) definition, "Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (e.g., networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction."

2. Five Essential Characteristics of Cloud Computing

  • 1. On-Demand Self-Service: A consumer can unilaterally provision computing capabilities—such as server time, virtual machines, and network storage—automatically via a web console or API without requiring human interaction with each service provider. Example: Launching an AWS EC2 instance in seconds.
  • 2. Broad Network Access: Capabilities are available over the network and accessed through standard mechanisms that promote use by heterogeneous thin or thick client platforms (e.g., mobile phones, tablets, laptops, and workstations).
  • 3. Resource Pooling (Multi-Tenancy): The provider's computing resources are pooled to serve multiple consumers using a multi-tenant model, with different physical and virtual resources dynamically assigned and reassigned according to consumer demand. Consumers generally have location independence (though they may specify region/country).
  • 4. Rapid Elasticity: Capabilities can be elastically provisioned and released—in some cases automatically—to scale rapidly outward and inward commensurate with demand. To the consumer, available capabilities often appear unlimited and can be appropriated in any quantity at any time.
  • 5. Measured Service: Cloud systems automatically control and optimize resource use by leveraging a metering capability at some level of abstraction appropriate to the type of service (e.g., storage, processing, bandwidth, active user accounts). Resource usage is monitored, controlled, and reported, providing transparency for both provider and consumer.

1. Introduction

Cloud computing did not emerge overnight; it evolved gradually over several decades from foundational computing paradigms aimed at sharing hardware, improving fault tolerance, and lowering operational costs.

2. Key Paradigms in the Evolution

  • 1. Mainframe & Time-Sharing (1950s–1960s): Multiple users accessed a centralized mainframe via dumb terminals, introducing the foundational concept of shared computing resources.
  • 2. Distributed Computing: Multiple autonomous computers connected over a network coordinate by passing messages to solve a common problem, appearing to the user as a single coherent system. It introduced horizontal scalability and fault tolerance.
  • 3. Cluster Computing: A group of tightly coupled, homogeneous commodity computers linked via high-speed local area networks (LAN) working together as a single integrated computing resource (e.g., Beowulf clusters) for high availability and parallel execution.
  • 4. Grid Computing: Connects geographically dispersed, heterogeneous computing resources across multiple administrative domains via middleware to solve large-scale scientific and engineering problems (e.g., SETI@home, CERN LHC Grid). Unlike clusters, grids are loosely coupled and heterogeneous.
  • 5. Utility Computing: Packages computing resources (computation, storage, bandwidth) as a metered service similar to traditional public utilities (electricity, water), charging users strictly on a pay-per-use basis.
  • 6. Virtualization & Web 2.0 (Modern Cloud): Hardware virtualization (hypervisors like Xen, VMware, KVM) decoupled software from physical hardware, enabling multi-tenancy and rapid provisioning. Combined with high-speed broadband and Service-Oriented Architecture (SOA), this birthed modern cloud computing (AWS EC2/S3 in 2006).

Benefits of Cloud Computing

Introduction

Cloud computing shifts organizations from owning and maintaining physical IT infrastructure to consuming scalable resources on demand, delivering significant technical and financial advantages.

  • 1. Cost Efficiency (CapEx to OpEx): Eliminates upfront Capital Expenditure (CapEx) on servers, data centers, and cooling, converting IT spending into a predictable Operational Expenditure (OpEx) where users pay only for consumed resources.
  • 2. On-Demand Scalability & Elasticity: Resources can scale up during traffic spikes (e.g., e-commerce flash sales) and scale down during idle periods automatically, preventing over-provisioning and under-utilization.
  • 3. Global Accessibility & Mobility: Applications and data are accessible 24/7 from any location and any internet-enabled device, supporting remote work and global collaboration.
  • 4. High Availability & Disaster Recovery: Cloud providers replicate data across multiple Availability Zones (AZs) and geographic regions, offering built-in backup, automated failover, and high SLA uptime (99.9%–99.99%).
  • 5. Speed & Agility (Faster Time-to-Market): Developers can provision servers, databases, and AI/ML services within minutes instead of waiting weeks for hardware procurement, accelerating innovation.
  • 6. Reduced Maintenance Burden: The cloud provider handles physical security, hardware repairs, power management, and (in PaaS/SaaS) OS and software patching.

1. Major Challenges of Cloud Computing

  • Security and Data Privacy: Storing sensitive data on shared third-party infrastructure introduces risks of data breaches, unauthorized access, insecure APIs, and multi-tenancy vulnerabilities.
  • Vendor Lock-In: Proprietary APIs, database formats, and management tools make migrating workloads from one cloud provider (e.g., AWS) to another (e.g., Azure) costly and complex.
  • Internet Connectivity Dependency & Latency: Cloud access relies entirely on stable, high-bandwidth internet; network outages halt operations, and distant data centers can introduce latency.
  • Compliance and Legal Governance: Organizations must comply with strict data sovereignty and privacy laws (such as GDPR, HIPAA, PCI-DSS, and RBI data localization guidelines), which dictate where data may physically reside.
  • Unexpected Cost Overruns: Poorly configured auto-scaling, idle unmonitored resources, or high data egress fees can inflate monthly cloud bills.
  • Limited Infrastructure Control: Users cannot inspect or customize the underlying physical hardware or hypervisor layer.

2. Major Applications of Cloud Computing

  • Web & Mobile Application Hosting: Scalable e-commerce platforms, SaaS portals, and social media apps (e.g., Amazon, Airbnb).
  • Big Data Analytics & AI/ML: Processing petabytes of data and training deep learning models using elastic GPU clusters (e.g., AWS EMR, Google BigQuery).
  • Backup, Storage & Disaster Recovery: Durable object storage and automated cross-region failover (e.g., Dropbox, Google Drive).
  • Media Streaming & Gaming: Global content delivery via CDNs and cloud gaming (e.g., Netflix, Spotify).
  • Healthcare & Education: Electronic Health Records (EHR), telemedicine platforms, and Learning Management Systems (LMS).

3. Scenario Analysis: Should a Banking Organization Shift Customer Data to a Public Cloud?

Verdict: No, not purely on a standard Public Cloud. Instead, the bank should adopt a Hybrid Cloud (or dedicated Financial Community/Private Cloud) architecture.

  • Regulatory & Data Sovereignty Compliance: Banking regulators (such as RBI in India, GDPR in Europe, and PCI-DSS globally) mandate strict data localization, auditability, and physical isolation for core banking and Personally Identifiable Information (PII).
  • Multi-Tenancy & Insider Risk: In a public cloud, physical hardware is shared among multiple tenants. Any hypervisor vulnerability or misconfiguration poses catastrophic financial and reputational risk.
  • Recommended Solution (Hybrid Cloud): Keep core customer ledgers, KYC records, and transaction databases in an on-premises Private Cloud with Hardware Security Modules (HSMs), while offloading non-sensitive, high-traffic workloads (such as public websites, customer analytics, and mobile UI front-ends) to a compliant Public Cloud.

1. Overview of Cloud Service Models (SPI Model)

Cloud computing services are primarily categorized into three foundational delivery models—Infrastructure as a Service (IaaS), Platform as a Service (PaaS), and Software as a Service (SaaS)—differentiated by how much of the IT stack is managed by the provider versus the customer.

2. Detailed Breakdown & Real-World Examples

  • 1. Infrastructure as a Service (IaaS): Provides fundamental virtualized computing resources (virtual servers, block/object storage, virtual networks) over the internet. The user installs and manages the OS, middleware, and applications, while the provider manages physical hardware and virtualization.
    Real-World Example: Amazon Web Services (AWS EC2 & S3), Microsoft Azure Virtual Machines, and Google Compute Engine (GCE).
  • 2. Platform as a Service (PaaS): Provides a complete managed runtime, development environment, database, and deployment tools so developers can build, test, and deploy applications without managing OS patches or servers.
    Real-World Example: Google App Engine, Heroku, and AWS Elastic Beanstalk.
  • 3. Software as a Service (SaaS): Delivers ready-to-use, centrally hosted software applications over the internet via a web browser or thin client on a subscription basis. The provider manages the entire stack.
    Real-World Example: Google Workspace (Gmail, Docs), Microsoft 365, and Salesforce CRM.

1. Four Cloud Deployment Models

A Cloud Deployment Model defines where the cloud infrastructure is located, who owns and manages it, and who has access to its resources.

  • 1. Public Cloud: Cloud infrastructure is provisioned for open use by the general public. It is owned, managed, and operated by a third-party Cloud Service Provider (CSP) on their premises using multi-tenant architecture.
    Examples: AWS, Microsoft Azure, Google Cloud Platform (GCP).
    Use Cases: Web hosting, startups, SaaS applications, dev/test environments, and burst workloads.
  • 2. Private Cloud: Cloud infrastructure is provisioned for exclusive use by a single organization comprising multiple business units. It may be hosted on-premises or by a third party and provides maximum security and customization.
    Examples: VMware vSphere private cloud, OpenStack, AWS Outposts.
    Use Cases: Banking/financial institutions, government agencies, defense, and organizations with strict regulatory compliance.
  • 3. Hybrid Cloud: A composition of two or more distinct cloud infrastructures (private, community, or public) that remain unique entities but are bound together by standardized or proprietary technology enabling data and application portability (e.g., cloud bursting).
    Use Cases: Healthcare and retail enterprises keeping sensitive customer PII on a private cloud while running public-facing portals and seasonal traffic bursts on a public cloud.
  • 4. Community Cloud: Cloud infrastructure is provisioned for exclusive use by a specific community of consumers from organizations that have shared concerns (e.g., mission, security requirements, policy, and compliance considerations).
    Use Cases: Consortium of hospitals sharing medical research data under HIPAA, universities collaborating on research grids, or state government departments.

1. Overview

Cloud Computing Architecture refers to the hardware and software components and sub-components required for cloud computing. It is broadly divided into two parts: the Front-End (client side) and the Back-End (cloud provider side), connected via a network (typically the Internet).

2. Major Components / Layers of Cloud Architecture

  • 1. Client Infrastructure (Front-End): Consists of user interfaces, web browsers, thin clients, mobile apps, and local networks required to access cloud applications.
  • 2. Application Layer: The top-most back-end layer where SaaS applications reside and are delivered directly to end-users.
  • 3. Service Layer: Manages the specific services offered (IaaS, PaaS, SaaS) along with APIs, service orchestration, and SLA enforcement.
  • 4. Cloud Runtime Layer: Provides the execution environment, virtual machines, containers, and OS runtimes required to run hosted code.
  • 5. Storage Layer: Ensures durable, scalable, and replicated storage of structured and unstructured data across distributed storage arrays.
  • 6. Infrastructure Layer: Comprises the physical servers, CPU, memory, networking switches, and the Hypervisor that abstracts physical hardware into virtual resources.
  • 7. Management & Security (Cross-Cutting Layers): Management coordinates resource provisioning, billing, monitoring, and load balancing; Security enforces IAM, encryption, firewalls, and compliance across all layers.

1. Definition & Role of Virtualization in Cloud Computing

Virtualization is the technology of creating a software-based (virtual) abstraction of physical computing resources—such as servers, storage devices, networks, or operating systems—allowing multiple isolated virtual environments to run concurrently on a single physical machine.

Role in Cloud Computing: Virtualization is the foundational enabling technology of cloud computing. It enables multi-tenancy (resource pooling), improves hardware utilization from ~15% to over 70–80%, isolates customer workloads securely, and allows rapid provisioning and live migration of Virtual Machines (VMs) on demand.

2. Types of Virtualization

  • 1. Server (Compute) Virtualization: Partitions a single physical server into multiple isolated Virtual Machines (VMs) using a hypervisor. Each VM runs its own guest OS and applications independently (e.g., VMware ESXi, KVM, Xen).
  • 2. Storage Virtualization: Pools physical storage capacity from multiple heterogeneous network storage devices (SAN/NAS) into a single logical storage unit managed from a central console (e.g., AWS EBS, VMware vSAN).
  • 3. Network Virtualization (SDN/NFV): Decouples network functions (switches, routers, firewalls, VLANs, load balancers) from physical hardware to create software-defined virtual networks (e.g., VMware NSX, AWS VPC).
  • 4. Desktop Virtualization (VDI): Hosts desktop operating systems on centralized data center servers and delivers them remotely to end-user thin clients (e.g., Citrix Virtual Apps, Amazon WorkSpaces).
  • 5. Application Virtualization: Encapsulates an application and its runtime dependencies away from the underlying OS so it can run without traditional installation (e.g., Microsoft App-V, Docker containers).
  • 6. Data Virtualization: Aggregates and queries data across distributed heterogeneous databases in real time without physically moving or replicating the data.

1. Resource Management & Four Resource Dimensions (General Q12 & Q13)

Resource Management in a virtualized cloud is the continuous monitoring, scheduling, and dynamic allocation of physical infrastructure capacity among competing Virtual Machines to satisfy SLAs without wasting energy.

  • CPU Allocation: Hypervisors schedule vCPUs onto physical CPU cores using time-slicing, weighted shares, CPU pinning (affinity), and reservation/limit caps.

  • Storage Allocation: Uses Thin Provisioning (allocating physical blocks only as data is written) and Storage I/O Control (IOPS throttling) to prevent disk bottlenecks.

  • Memory Contention Fixes: Activate the Memory Balloon Driver inside guest VMs to reclaim unused free pages from low-priority VMs and reassign them to memory-hungry VMs, or scale out horizontally.

Virtualization Tools, Techniques & Implementation Levels

Original Question Bank Mapping (2 Questions):

  • General Ch.2 Q20: Explain implementation levels of virtualization.
Cross-Bank Mapping: Combines General Ch.2 Q14 and Q20.

1. Virtualization Techniques

  • Full Virtualization: Completely simulates underlying hardware using binary translation (e.g., VMware ESXi); unmodified guest OS runs unaware it is virtualized.
  • Paravirtualization: Guest OS kernel is modified to communicate directly with the hypervisor via hypercalls for higher I/O efficiency (e.g., Xen).
  • Hardware-Assisted Virtualization: Uses CPU extensions (Intel VT-x and AMD-V) so privileged guest instructions trap directly to the hypervisor without software binary translation (e.g., KVM).
  • OS-Level Virtualization: Shares host kernel to run isolated containers (e.g., Docker, LXC).

2. Five Implementation Levels of Virtualization (General Q20)

  1. Instruction Set Architecture (ISA) Level: Emulates one CPU ISA on another via code interpretation/binary translation (e.g., QEMU, Rosetta).
  2. Hardware Abstraction Layer (HAL) Level: Maps virtual hardware directly to physical hardware via hypervisors (e.g., KVM, ESXi, Hyper-V).
  3. Operating System Level: Partitions a single OS into isolated user-space containers (e.g., Docker, OpenVZ).
  4. Library (User-Level API) Level: Intercepts API/ABI calls between applications and OS libraries (e.g., WINE, vCUDA).
  5. Application (Programming Language) Level: Runs applications inside a process virtual machine bytecode runtime (e.g., JVM for Java, CLR for .NET).

Virtual Machine Migration & Step-by-Step Live VM Migration Process

Original Question Bank Mapping (2 Questions):
  • General Ch.2 Q19: Explain Virtual Machine migration as a virtualization technique.
  • IMP Unit-2 Q6: Detail out the steps involved in a Live VM Migration.
Cross-Bank Mapping: Merges General Ch.2 Q19 and IMP Unit-2 Q6.

1. What is Virtual Machine Migration?

VM Migration is the process of moving a Virtual Machine from one physical host server (or storage location) to another. It enables proactive hardware maintenance, dynamic load balancing, power-saving server consolidation, and fault avoidance.

  • Cold (Offline) Migration: The VM is powered off, its configuration and disk files are moved to the destination host, and it is restarted (causes downtime).
  • Live (Hot) Migration: A running VM is transferred between physical hosts with near-zero perceptible downtime (typically < 100 milliseconds), preserving active network connections and in-memory state.

2. Six Steps in Pre-Copy Live VM Migration (IMP Unit-2 Q6)

  1. Step 1 – Pre-Migration: An active VM runs on Source Host A. Management software selects Destination Host B and checks compatibility (CPU family, shared SAN/NAS storage access).
  2. Step 2 – Reservation: Resources (CPU, RAM, network ports) are reserved on Destination Host B to guarantee capacity for the incoming VM.
  3. Step 3 – Iterative Pre-Copy: While the VM continues running on Host A, all memory (RAM) pages are copied to Host B. Modified ("dirty") pages during transfer are iteratively re-copied in subsequent rounds until the dirty page rate drops below a small threshold.
  4. Step 4 – Stop-and-Copy: The VM on Host A is briefly suspended (milliseconds), and the final remaining dirty memory pages along with CPU register states are copied to Host B.
  5. Step 5 – Commitment: Host B confirms receipt of a consistent VM image; Host A discards its original VM state and releases its resources.
  6. Step 6 – Activation: The VM resumes execution on Host B, and an unsolicited Gratuitous ARP packet updates physical network switches to route traffic to Host B's port.

1. Definition & Major Functions of IAM (General Q3 & Q4)

Identity and Access Management (IAM) is a security framework of policies and technologies that ensures the right entities (users, applications, services) have the appropriate level of access to cloud resources at the right time.

  • Authentication (AuthN): Verifying who a user or service is (via passwords, MFA tokens, SSH keys, or X.509 certificates).
  • Authorization (AuthZ): Determining what actions an authenticated identity is permitted to perform on specific resources via granular JSON/YAML policies.
  • Role-Based Access Control (RBAC): Assigns permissions to functional Roles (e.g., ReadOnlyAuditor, DatabaseAdmin) rather than individual users, simplifying permission governance at scale.
  • Identity Federation & SSO: Integrates corporate directories (Active Directory, Okta) using SAML 2.0 or OIDC so users log in once.
  • Auditing & Credential Lifecycle: Automated key rotation, temporary session tokens, and access logging (e.g., AWS CloudTrail).

2. Steps to Implement IAM in Cloud (IMP Unit-4 Q2)

  1. Lock Down Root Account: Enable hardware/app MFA on the root account and never use it for daily tasks.
  2. Create Individual Identities & Groups: Provision unique user accounts grouped by job function.
  3. Enforce Least Privilege via RBAC Policies: Grant only the minimum permissions required for each role.
  4. Mandate Multi-Factor Authentication (MFA): Require MFA across all console and privileged CLI sessions.
  5. Use Temporary IAM Roles for Services: Assign short-lived STS tokens to VMs/containers instead of hardcoding static API keys.
  6. Continuous Auditing & Key Rotation: Monitor access logs and rotate credentials every 60–90 days.

3. Scenario Analyses (Twisted Ch.4 Q2, Q3 & Q9)

  • Read-Only Enforcement (Twisted Q2): Attach an IAM Authorization Policy explicitly allowing GetObject / Select actions while explicitly denying (or omitting) PutObject, Update, and Delete actions on the target resource.
  • Risks of Admin Privileges for Everyone (Twisted Q3): Violates the Principle of Least Privilege; a single phished employee account or accidental CLI command can delete production databases, alter firewall rules, or spin up expensive crypto-mining VMs.
  • Unauthorized Access Despite Strong Passwords (Twisted Q9): Strong passwords alone cannot stop phishing, session hijacking, or leaked API keys. Strengthen IAM by enforcing Multi-Factor Authentication (MFA), IP/VPC Conditional Access policies, short-lived temporary tokens, and anomalous login alerts.

1. Definition & Importance of SLA

A Service Level Agreement (SLA) is a legally binding contract between a Cloud Service Provider (CSP) and a customer that defines the guaranteed quality, availability, performance, responsibilities, and financial penalties (service credits) if service standards are violated. SLAs establish measurable trust, accountability, and business continuity expectations.

2. Important Contents & Metrics of an SLA (General Q13 & IMP Unit-4 Q3)

  • Availability / Uptime Guarantee: Percentage of time the service is operational (e.g., 99.9% = ~43.8 mins downtime/month; 99.99% = ~4.38 mins downtime/month).
  • Performance & Latency Metrics: Maximum response time, throughput (IOPS/bandwidth), and error rate thresholds.
  • Incident Response & Resolution Times: Mean Time to Detect (MTTD), Mean Time to Respond (MTTR), and 24/7 support escalation tiers.
  • Data Durability, Backup & Disaster Recovery: Recovery Time Objective (RTO) and Recovery Point Objective (RPO).
  • Exclusions & Service Credits: Scheduled maintenance windows excluded from downtime, and billing credit percentages refunded upon SLA breach.

3. Six Stages of the Cloud SLA Lifecycle

  1. Discover & Define: Customer identifies QoS requirements and compares provider SLA templates.
  2. Negotiate & Sign: Parties finalize custom enterprise terms, penalties, and compliance clauses.
  3. Provision & Deploy: Cloud resources are allocated with monitoring hooks configured.
  4. Monitor & Measure: Continuous telemetry tracks uptime, latency, and packet loss against SLA thresholds.
  5. Manage & Remediate (Penalty Enforcement): If violations occur, alerts trigger remediation and service credits are claimed.
  6. Terminate / Renew: Contract is either renegotiated upon expiry or cleanly terminated with verified data deletion.

4. SLA Concerns When Repeated Downtime Occurs (Twisted Ch.4 Q4)

  • Monthly Uptime Calculation & Exclusions: Providers often exclude "scheduled maintenance" or single-AZ failures if the customer failed to deploy across multiple Availability Zones.
  • Inadequate Remedies: Service credits (typically 10%–25% of monthly bill) rarely compensate for actual business revenue loss.
  • Claim Burden & Exit Clauses: Customers must submit log proof within strict windows; chronic SLA breaches should trigger contractual termination without penalty and multi-region failover architecture.

  • Fog Computing: Introduced by Cisco; acts as an intermediate decentralized computing tier between edge devices and the centralized cloud, running on local area network (LAN) routers, gateways, and micro-data centers. Applications: Smart city traffic grids, connected rail/power substations.

1. Load Balancing: Definition, Need & Algorithms (General Q6–Q8 & IMP Unit-5 Q3)

A Load Balancer is a networking service/appliance that automatically distributes incoming client traffic across multiple backend virtual machines or containers so no single server becomes overwhelmed.

  • Why It Is Used: Prevents server overload, maximizes throughput, minimizes response time, performs continuous health checks to reroute traffic away from failed instances (high availability), and enables zero-downtime rolling updates.
  • Common Load Balancing Algorithms:
    1. Round Robin (Static): Distributes incoming requests sequentially to each server in the pool in circular order (Server 1 → 2 → 3 → 1). Best when all servers have identical specs.
    2. Least Connections (Dynamic): Routes new requests to the server currently holding the fewest active client connections. Ideal for requests with varying processing durations.
    3. Weighted Round Robin / IP Hash: Assigns higher request ratios to larger instances or pins client IPs for session persistence.

2. Auto Scaling: Definition & Performance/Cost Impact (General Q9, IMP Unit-5 Q6 & Twisted Q10)

Auto Scaling is a cloud capability that automatically monitors application metrics (CPU utilization, request count, queue depth) and dynamically adds or removes compute instances based on user-defined scaling policies.

How It Improves Both Performance & Cost (Twisted Q10): During sudden traffic surges, Auto Scaling scales out new instances to maintain low latency and prevent crashes (performance); during off-peak night hours, it scales in and terminates unneeded VMs so the organization pays zero idle compute charges (cost efficiency).

1. Cloud Monitoring & Important Metrics (General Q11 & Q12)

Cloud Monitoring is the continuous collection, visualization, and alerting on operational telemetry logs and metrics across cloud infrastructure and applications (e.g., AWS CloudWatch, Azure Monitor, Prometheus/Grafana).

  • Compute Metrics: CPU Utilization (%), CPU Credit Balance, Memory (RAM) usage, and Swap activity.
  • Storage Metrics: Disk Read/Write IOPS, Disk Queue Depth, and Volume Throughput (MB/s).
  • Network Metrics: Network In/Out bandwidth, Packet Drop Rate, and DNS/TCP latency.
  • Application & Availability Metrics: Request Latency (p95/p99), HTTP 4xx/5xx Error Rates, and Health Check status.

2. Diagnostic Scenario: Service is Slow Despite Low CPU Utilization (Twisted Ch.5 Q4)

  • Possible Non-CPU Bottlenecks: (1) Database lock contention / unindexed slow SQL queries; (2) Disk IOPS exhaustion (high disk queue depth); (3) Memory exhaustion causing disk swapping; (4) External downstream API latency or network bandwidth throttling; (5) Thread-pool / connection-pool exhaustion.
  • Optimization Methods: Add an in-memory cache (Redis / Memcached) in front of the database, upgrade storage to provisioned high-IOPS SSDs, introduce a CDN for static assets, optimize SQL indexes, and enable asynchronous message queues (SQS/Kafka) for heavy background jobs.
